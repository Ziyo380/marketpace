# Исправления Backend Audit

Дата: 19 ноября 2026. Закрыты шесть воспроизводимых ошибок A01–A06 из первичного аудита. Отдельные риски производительности и эксплуатации из того отчёта остаются самостоятельными задачами; эта работа не заменяет внешний pentest или нагрузочное тестирование.

## Изменения

| Ошибка | Исправление | Проверка |
|---|---|---|
| A01: товар отключённой категории покупался | Проверка Category.active в checkout, добавлении и изменении корзины | Отказ после отключения категории, количество корзины не меняется |
| A02: название с вариантом не помещалось в заказ | Entity и новая V36 увеличивают product_name до VARCHAR(323) | Сохраняются полностью 200 + 3 + 120 символов |

Старые SQL-миграции не изменялись. Добавлены:

- `V36__expand_order_item_product_name.sql` — расширение исторического названия без обрезания данных.
- `V37__create_storage_deletion_tasks.sql` — постоянная очередь удаления объектов, индекс очередных попыток, UNIQUE object_key и счётчик попыток.

Действующая цепочка заказа, публичные URL и форматы успешных ответов сохранены. Код фронтенда в этой работе не изменялся.

## Как теперь удаляются фотографии

1. `ProductImageService` проверяет владельца и удаляет запись фотографии. В этой же транзакции `StorageCleanupService` сохраняет `StorageDeletionTask`.
2. До commit физический файл остаётся на месте. Если транзакция откатывается, запись фотографии и файл сохраняются, задача удаления откатывается вместе с ней.
3. После commit `StorageDeletionProcessor` в отдельной транзакции пытается удалить объект. Задача блокируется через PESSIMISTIC_WRITE, чтобы несколько обработчиков не выполняли её одновременно.
4. После успешного удаления задача удаляется. Если хранилище недоступно, задача остаётся в БД с датой следующей попытки. Интервал повтора увеличивается от минуты до часа.
5. Фоновая проверка берёт максимум 50 готовых задач раз в минуту (`storage.cleanup-check-ms`, по умолчанию 60000). После перезапуска процесса очередь сохраняется.

Для загрузки добавлена компенсация **после rollback**, включая откат после возврата из `uploadImage()`. Если компенсационное удаление не удалось, оно тоже остаётся в очереди. Если сама БД недоступна в момент записи такой компенсации, ошибка журналируется; абсолютной атомарности PostgreSQL и внешнего object storage этот механизм не обещает. Остановка процесса между загрузкой файла и регистрацией/выполнением компенсации также требует отдельного поиска файлов без ссылок.

При сбое хранилища удаление фотографии из интерфейса считается завершённым после commit БД; физический объект будет удалён повторной попыткой. Это предотвращает восстановление ссылки на уже удалённый файл при rollback. Повторное удаление отсутствующего объекта должно оставаться идемпотентным для используемых storage-адаптеров.

## Проверки

Полный запуск: **84 теста в 19 наборах, 0 failures, 0 errors, 0 skipped**. `bootJar` собран успешно.

- 74 проверки обычного test source set, включая 21 сценарий `BackendAuditRegressionTest` и новый тест общего обработчика 403.
- 9 повторных сценариев доставки/истории на PostgreSQL.
- 1 проверка обновления исторических заказов V30 → V37 с сохранением сумм и неизвестного распределения скидок.

Проверки бывших ошибок перенесены из opt-in файла в `src/test/java/com/marketplace/audit/BackendAuditRegressionTest.java`, поэтому входят в обычный набор. Для PostgreSQL нужен Docker; без него этот класс помечается пропущенным. Указанный полный прогон выполнен с Docker, пропусков не было.

Команда из корня backend с Java 21:

```powershell
.\gradlew.bat test bootJar --offline --no-daemon --max-workers=1 '-Dorg.gradle.jvmargs=-Xmx256m -Xms64m -XX:MaxMetaspaceSize=256m -XX:ReservedCodeCacheSize=64m -XX:ActiveProcessorCount=2' --init-script docs/audit/probes/low-memory.init.gradle --init-script docs/audit/probes/audit-probes.init.gradle
```

Если зависимости ещё не загружены, убрать `--offline`. Второй init script дополнительно подключает PostgreSQL-повтор доставки и проверку обновления миграций. Обычный `test` содержит regression-проверки шести исправлений и без этого script.

Доказательства: `evidence/remediation-tests.json` и `evidence/remediation-source-manifest.json`. Исходные красные результаты аудита сохранены отдельно и описывают состояние **до исправлений**. Проверки файлов выполнялись во временном каталоге, изменяющие данные тесты — в одноразовых PostgreSQL 17. Действующие пользовательские заказы этими тестами не изменялись. Живой MinIO отдельно не проверялся; его существующий unit test также прошёл.

## Проверка запущенного приложения

Собранный backend перезапущен на 8080. Локальная рабочая PostgreSQL успешно применила V36 и V37, проверены все 37 миграций и соответствие Entity схеме. Оба фронтенда на 3000 и 4200 отвечают 200.

Через реальный HTTP повторно проверены 8 существующих демонстрационных заказов, 7 доставок, 30 событий истории и изображения 32 публичных демо-товаров. Обращение действующего другого пользователя к чужим доставкам получило **403 FORBIDDEN_OPERATION**. Новые заказы или удаления фотографий в рабочей базе не выполнялись. Сохранён `evidence/remediation-live-smoke.json`.

При перезапуске предпросмотра создан новый JWT secret в окружении процесса; прежние access token нужно заменить повторным входом. Данные пользователей сохраняются.
