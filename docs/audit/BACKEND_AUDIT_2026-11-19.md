## Подтверждённые ошибки

### A01 — P1: отключённая категория не запрещает checkout

**Место:** `src/main/java/com/marketplace/order/service/OrderCreationService.java:92` — цикл проверки доступности товаров. Аналогичная проверка отсутствует в `CartService.addItem()`.

**Сценарий:** покупатель положил товар в корзину; администратор отключил категорию; покупатель оформил заказ. Заказ создаётся, хотя публичный каталог уже исключает такие товары через `Category_ActiveTrue`.

**Доказательство:** `checkoutMustRejectCategoryDisabledAfterCartWasFilled()` завершился ошибкой: ожидаемое исключение не возникло, checkout состоялся.

**Последствие:** правила доступности каталога и оформления расходятся. Скрытый товар можно купить из старой корзины; при известном UUID отсутствует и соответствующая защита добавления в корзину.

**Исправление:** проверять актуальную активность категории при checkout и добавлении/изменении корзины; возвращать согласованную бизнес-ошибку. Проверку при оформлении сохранить независимо от проверок корзины. Если запрет должен действовать строго одновременно с административным отключением, отдельно определить синхронизацию этих операций: обычная проверка значения не закрывает такую гонку сама по себе.

### A02 — P2: допустимое название товара с вариантом ломает оформление

**Место:** `OrderCreationService.java:163`; `src/main/java/com/marketplace/order/entity/OrderItem.java:38`.

DTO допускают название товара длиной 200 и варианта длиной 120 символов. Checkout склеивает их через ` — `: получается до **323 символов**, тогда как `order_items.product_name` и Entity ограничены 255.

**Доказательство:** `validProductAndVariantNamesMustFitOrderSnapshot()` — PostgreSQL вернул `value too long for type character varying(255)`, Spring выбросил `DataIntegrityViolationException`.

**Последствие:** корректные по контракту товары нельзя купить; транзакция откатывается. Через текущий общий обработчик такое исключение приводит к 500.

**Исправление:** согласовать размер исторического снимка с разрешёнными входными данными. Увеличить колонку отдельной новой миграцией и длину в Entity либо хранить снимки названий раздельно. Молча обрезать исторические данные нежелательно. Старые миграции не переписывать.

### A03 — P2: приостановленный продавец продолжает менять варианты

**Место:** `src/main/java/com/marketplace/product/service/ProductVariantService.java:162`, метод `ownedProduct()`.

Проверяется принадлежность товара магазину, но отсутствует проверка `SellerStatus.APPROVED`. Также нет проверки активности/одобрения магазина, которая существует в других сервисах управления товарами. Роль `SELLER` сама по себе не означает одобренный профиль продавца.

**Доказательство:** `suspendedSellerMustNotCreateVariants()` — после установки `SUSPENDED` запрос создания варианта получил **201**, ожидаемый запрет не сработал.

**Последствие:** приостановка продавца непоследовательно ограничивает управление товарами и складом вариантов. Доступ к чужим товарам этим тестом не обнаружен; речь об управлении собственным магазином после приостановки.

**Исправление:** применить согласованное правило допуска к изменению вариантов и их остатков. Для чтения истории и исполнения уже принятых заказов правила стоит определить отдельно: их нельзя автоматически запретить только потому, что запрещена продажа новых товаров.

### A04 — P2: отказ в доступе к чужой доставке возвращает 500

**Место:** `src/main/java/com/marketplace/delivery/service/ShipmentService.java:81`; `src/main/java/com/marketplace/common/exception/GlobalExceptionHandler.java:171`.

Сервисы доставки/истории выбрасывают Spring `AccessDeniedException`. Advice обрабатывает собственный `ForbiddenOperationException`, но Spring-исключение попадает в обработчик `Exception.class` раньше стандартного оформления отказа Security.

**Доказательство:** `foreignCustomerShipmentAccessMustReturn403()` — запрос `GET /api/v1/orders/{чужойOrderId}/shipments` с действительным JWT вернул **500 вместо 403**.

**Последствие:** неверный контракт ошибок, ложные аварии в мониторинге и путаница на фронтенде. **Чужие данные запросу не выданы.** Это не доказанный обход ownership.

**Исправление:** согласовать исключения сервисов с общим `ErrorResponse`: отдельная обработка Spring `AccessDeniedException` либо единое прикладное исключение. Проверить и seller/customer endpoints истории. Отказы фильтра Security и ошибки MVC нужно проверять отдельно: роль без доступа в текущем тесте корректно получила 403.

### A05 — P2: цена варианта принимает лишнюю точность

**Место:** `src/main/java/com/marketplace/product/dto/request/CreateProductVariantRequest.java:13`; `UpdateProductVariantRequest.java:10`.

Есть `@DecimalMin`, но нет ограничения количества цифр, соответствующего `NUMERIC(19,2)`. У обычного Product такое ограничение уже есть.

**Доказательство:** `variantPriceWithThreeDecimalsMustBeRejected()` — POST с `price=100.005` получил **201 вместо 400**. PostgreSQL допускает приведение к масштабу колонки, поэтому ввод не отклоняется на границе API.

**Последствие:** клиент может получить принятое значение, отличающееся от сохранённой денежной суммы; чрезмерная целая часть также не отсекается этой DTO-валидацией.

**Исправление:** согласовать create/update DTO и сервисную границу с 17 цифрами целой части и 2 дробными. Проверить денежные поля промокодов и зон доставки на то же правило; для них в рамках аудита отдельные отрицательные сценарии не запускались.

### A06 — P2: откат удаления фотографии оставляет битую ссылку

**Место:** `src/main/java/com/marketplace/product/service/ProductImageService.java:180`.

Файл удаляется из object storage **до фиксации транзакции БД**. Откат PostgreSQL не восстанавливает файл.

**Доказательство:** `imageMustRemainReadableWhenDatabaseDeletionRollsBack()` загрузил PNG в отдельный временный каталог, удалил фотографию внутри транзакции и принудительно откатил её. Запись ProductImage осталась в БД, физический файл отсутствует.

**Последствие:** потеря фотографии при неуспешном удалении; фронтенд показывает ссылку на отсутствующий файл. Сценарий проверен на локальном storage. Вызов удаления MinIO находится на той же границе транзакции, но отдельный живой MinIO в этом аудите не поднимался.

**Исправление:** выполнять физическое удаление после успешного commit и предусмотреть повтор при сбое storage. Должно быть явно определено, как удалять оставшиеся файлы после такого сбоя. Отдельно проверить компенсацию неуспешной загрузки при ошибке на позднем commit.

## Что подтверждено работающим

### Security и ownership

- Отсутствующий и некорректный JWT не дают читать заказы: 401.
- После блокировки User прежний корректно подписанный access token не даёт доступа: 401.
- Покупатель не может вызвать подтверждение SellerOrder: 403.
- Чужой действующий продавец не может получить товар другого магазина: 404.
- Чужой покупатель не может получить заказ, чужой продавец не может подтвердить его часть: 404 в сквозном сценарии.
- Роли поднимаются из БД; фильтр проверяет активность User. Refresh token хранится в виде SHA-256, выдаётся из случайных байтов и потребляется с блокировкой. Повторное использование старого refresh token после ротации получило 401.

Эти проверки не заменяют полную матрицу всех маршрутов и всех комбинаций ролей. Дефект A04 показывает, почему проверки одного Service недостаточно для проверки конечного HTTP-ответа.

### Checkout, остатки и отмена

Штатные PostgreSQL-тесты подтвердили:

- создание частей заказа для двух магазинов и соответствующих резервов;
- историческую цену, очистку корзины, работу выбранного SKU;
- откат оформления при недостаточном остатке;
- отсутствие двойного резерва последней единицы в проверенном конкурентном сценарии;
- один результат при повторном Idempotency-Key;
- один заказ при одновременном оформлении одной существующей корзины;
- согласованную отмену покупателем и продавцом;
- согласованность при конкурентном подтверждении продавцом и отмене покупателем;
- освобождение просроченных резервов.

В коде действительно есть `PESSIMISTIC_WRITE` для существующей корзины и родительского Order, а также `@Version` у остатков/резервов/заказов. Названия методов не использовались как единственное доказательство блокировки.

### Pricing

Проверены начисление доставки один раз, применение/освобождение промокода, распределение остаточной копейки скидки, неизменность исходной суммы при частичной отмене и уменьшение текущей суммы обязательства.

`totalAmount` — снимок оформления; `currentTotalAmount` — сумма неотменённых частей. Их различие после частичной отмены предусмотрено моделью. Для исторических заказов неизвестное распределение скидки сохраняется как `NULL`, а не заменяется выдуманными значениями.

### Delivery и история

Все девять сценариев `ShipmentHistoryIntegrationTest` дополнительно выполнены на PostgreSQL 17 через `ShipmentHistoryPostgresAuditTest`:

- цепочка создания, сборки, отправки и вручения;
- повторные операции без дублирования событий;
- причина неудачной доставки;
- ownership истории;
- откат Shipment при сбое сохранения истории;
- откат изменений Shipment, общего статуса и истории Order при ошибке;
- обязательность общей транзакции для записи истории;
- параллельное вручение частей разных магазинов;
- завершение доставленной части при наличии ожидающей части и последующее истечение её резерва.

Дополнительный сквозной сценарий проходит регистрацию → login → refresh/отказ повторного refresh → корзину → checkout/повтор ключа → подтверждение продавцом → PACKING → READY_FOR_DISPATCH → IN_TRANSIT → DELIVERED. После повторного вручения история содержит 5 событий, корзина пуста, общий заказ DELIVERED.

Этот сценарий проходит через настоящие фильтры Security, Controller и Service с PostgreSQL, используя **MockMvc внутри приложения**. Это не браузерный E2E и не сетевой тест развернутого Docker backend.

## PostgreSQL и миграции

- Чистая PostgreSQL 17 успешно прошла миграции **V1–V35** и JPA schema validation в интеграционных тестах.
- Отдельная PostgreSQL сначала создана на V30; добавлены исторические PENDING, PARTIALLY_CANCELLED и CANCELLED заказы и шесть частей магазинов; затем применены V31–V35 и `Flyway.validate()`.
- Проверены сохранение исходных сумм/скидок и количества записей, начальный delivery total, `current_total_amount` для трёх состояний, сохранение неизвестных discount/payable у старых SellerOrder.
- Следовательно, V31/V32 и последующие теперь подтверждены на реальной PostgreSQL, в том числе при таком обновлении старой схемы.
- Это не восстановление копии реальной клиентской БД: произвольные повреждённые данные и все возможные исторические состояния не охвачены.
- `order_items.seller_order_id` и `product_name` уже сделаны NOT NULL миграцией V18. Старый пункт плана «сделать обязательными» больше не является незавершённой задачей.

## Качество и производительность — отдельные риски

Эти пункты найдены чтением кода и не выдаются за измеренные нагрузочные дефекты:

1. **Риск N+1 при списке заказов.** `OrderRepository.java:30` возвращает Page без плана загрузки связей; `OrderMapper.java:19` читает sellerOrders, затем Mapper читает items. Перед оптимизацией измерить количество SQL на странице с несколькими магазинами/позициями. Использовать пакетную загрузку или выборку ID страницы с последующей загрузкой связей; обычный fetch join нескольких коллекций вместе с пагинацией нельзя добавлять без проверки результата.
2. **Неограниченные списки истории/движений.** `InventoryMovementRepository.java:9` и история заказов возвращают полный List; expiry job также выбирает все просроченные ID сразу. По мере роста данных нужны ограниченные выборки/пакеты и подходящие индексы.
3. **Не все конфликты БД оформлены как управляемые ошибки.** Есть общий 409 для optimistic locking, но гонки UNIQUE, deadlock/lock timeout могут попасть в catch-all 500. Дубликаты SKU/slug/username проверяются до сохранения, что само по себе не защищает от параллельной вставки. Сначала воспроизвести конкретную гонку, затем выбрать её семантику; автоматически повторять любую денежную транзакцию нельзя.
4. **Создание первой корзины.** Блокировка существующей строки не блокирует отсутствие корзины. Параллельные первые запросы могут столкнуться с UNIQUE пользователя. Это потенциальная ошибка ответа, а не доказанное создание дублирующих корзин.
5. **16 файлов с тестовыми именами без тестовых методов.** Среди них AuthServiceTest, CartServiceTest, ProductServiceTest, PromocodeServiceTest, InventoryConcurrencyIntegrationTest. Они не дают покрытия. Процент покрытия кода не измерялся.
6. **Границы регистрации/login.** В DTO регистрации нет верхней границы пароля, login ограничен только NotBlank. Следует согласовать ограничения с фактическим BCrypt и проверить длинные/многобайтовые значения. Отдельный негативный тест этого ограничения в текущем прогоне не выполнялся.
7. **Защита эксплуатации.** Ограничение частоты login/register, production-секреты, TLS, резервное копирование/восстановление, метрики и доступность инфраструктуры требуют отдельной проверки конфигурации запуска. Статический просмотр приложения не подтверждает их наличие во внешнем reverse proxy.

## Как повторить

Из корня backend с Java 21 и работающим Docker:

```powershell
.\gradlew.bat test --no-daemon --max-workers=1 --init-script docs/audit/probes/low-memory.init.gradle
```

Отдельный аудит, включая известные красные проверки:

```powershell
.\gradlew.bat test --tests '*Audit*Test' --no-daemon --max-workers=1 --init-script docs/audit/probes/low-memory.init.gradle --init-script docs/audit/probes/audit-probes.init.gradle
```

На этой машине дополнительно применялся низкий лимит памяти Gradle daemon:

```text
-Dorg.gradle.jvmargs=-Xmx256m -Xms64m -XX:MaxMetaspaceSize=256m -XX:ReservedCodeCacheSize=64m -XX:ActiveProcessorCount=2
```

Зависимости уже были в локальном кеше, поэтому фактические прогоны использовали `--offline`. Если кеш пуст, этот флаг не использовать. Низкие лимиты предназначены для экономии памяти, а не для измерения производительности.

`probes/` не входит в обычный source set. Он подключается только вторым init script. Обычный `test` не должен становиться красным из-за ожидаемо падающих доказательств аудита. Команда аудита сейчас возвращает код **1** из-за шести подтверждённых ошибок, штатная — **0**.

Доказательства: `evidence/baseline-tests.json`, `evidence/audit-probes.json`, `evidence/source-manifest.json`. HTML последнего запуска: `build/reports/tests/test/index.html`.

После тестов восстановлены backend на 8080, покупательский frontend на 3000 и кабинет на 4200. Оба фронтенда и API регионов ответили 200. Существующий `scripts/verify-showcase.ps1` по реальной сети проверил 8 демо-заказов, 7 доставок, 30 событий истории и доступность изображений 32 публичных демо-товаров. Сохранён `evidence/live-smoke.json`. Проверка читает рабочие заказы; новые заказы не оформляет. Это smoke-проверка доступности и согласованности демонстрационных данных, а не проверка всех действий в браузере.

Автоматический анализ актуальных CVE зависимостей, полноценный внешний pentest, нагрузочные испытания, реальная оплата/возврат денег, интеграция с внешним перевозчиком и браузерные сценарии всех экранов не выполнялись. Живой MinIO не использовался: основной storage-сценарий проверялся на локальном хранилище, существующий тест MinIO проверяет формирование ссылки. Модули, которых ещё нет, не добавлялись. Успешные тесты заказа не означают готовую финансовую систему или гарантированное отсутствие уязвимостей.
